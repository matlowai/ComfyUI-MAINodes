## What is worth keeping

- Exact, inspectable strategy definitions and scoped parameter notes in existing records fit R60/R93. Their useful promise is that two productions can choose different approaches without a fork or global preference bleed.
- Native operations and Work/proposal/critic ownership remain intact. Guarded materialization is a reasonable response to having inspected source without a complete authoring checkout. The small native-file diff does not mean the delivered feature is small: all new files and their runtime interfaces need review.
- The distinction between reference evidence and sampler conditioning is valuable and directly follows the measured master/key pull failures in R242. Reuse this distinction at the native compiler boundary.
- Shot packing is a useful proposal when the caller actually supplies timing and engine constraints. Its oracle checks validate partitioning; they do not validate dramatic pacing or speech estimates.
- The bundle is unusually explicit about unperformed browser/GPU work and deferred spatial/temporal capabilities. Preserve those boundaries in the product vocabulary.

## Findings and required handling

### A1 — High: method-scoped instructions are absent from the original preview

**Proven source behavior.** `overlay/web/snap/director/host.mjs:59` always supplies `methods: []` and `bricks: []`. `service.mjs:67` obtains extra tool contexts for boards, edits and upscales, but never supplies the selected method. Native `web/snap/instructions.js:95` matches method scopes only through `c.methods.includes(rest)`. Thus a person's `method:qwen21_view` note cannot appear in this preview, even when a planned board explicitly selects that method. `DESIGN_DECISIONS.md` §9 overstates this as method-specific context being read. Actual execution can still recover the note if the agent follows the skill, but the preview's claimed effective preferences/provenance are incomplete.

**Fix in the integration:** resolve the effective method through its native owner, then request the corresponding instruction context before finalizing that operation's parameters. An inherited method needs its actual native default or an explicit unresolved status. Do not borrow the unrelated open graph's methods. If the method-specific note changes the method again, expose the disagreement or settle it under a defined rule; do not make an unbounded resolver. Recast must use the effective `remake_swap` context.

**Qualification:** native/injected-host tests with distinct method notes for Qwen, P-H3, edit, recast and upscale; a shot override must leave its sibling unchanged. Compare the resulting instruction refs with the native resolver, not just a hand-written fixture matcher. This finding was sent to the integration owner, who acknowledged and began a two-pass fix. No fix verification is claimed here.

### A2 — High for continuity claims, medium for this limited planner: reference proposals and executed references are disconnected

**Proven boundary, acknowledged by the author.** `planner.mjs:46` compiles a caller-supplied `reference_packet`; `planner.mjs:277` returns it under helpers. It does not produce or check the actual `apply_unit` package. `references.mjs:69` assesses declared top/side metadata; its return explicitly sets `visually_verified:false` and `profile_verified_against_live_graph:false`. A valid helper result can therefore coexist with different native sockets, an obsolete source frame, or an incompatible graph/model choice. The raw serialized prompt from this helper must never become a competing graph compiler.

**Integration requirement:** keep these results visibly labeled proposals. In the first executed slice, compare exact source refs/versions/frame indices, retained/excluded roles and final native prompt order before rendering. A passing packet is insufficient evidence.

**Highest-value follow-on:** expose a read-only reference packet from the existing board/compile owner, then display proposal versus actual compilation for one cut. Reuse its final identity/order/model semantics. Add only the small adapter needed; no new compiler, profile registry or scene database. R2, R242, R252, R270 and R271 govern it.

### A3 — Medium: the human entry is an agent debugging console before it is a production workflow

**Proven UI source, not a screenshot judgment.** `dialog.mjs:54` requires an entered Book reference; line 57 uses JSON for ordinary preferences; line 121 defaults saved preference scope to `global`. `web/snap_director.js` opens the dialog without current Book/shot context. A creator already working in a Book must know internal IDs, and a routine tweak naturally starts as a cross-production setting. It is visible, not hidden, but the default works against the advertised isolation benefit.

**Small fix:** open in the selected Book/cut context where available and default saved notes to that Book. Keep a clear explicit whole-install/person scope choice. Offer ordinary controls for candidate count/reuse/method choice as appropriate, retaining full JSON in Advanced. Do not build a new wizard. At minimum, fix scope/context before calling the UI creator-ready. The integration owner has been told about this default.

**Qualification:** actual visible Snap screenshot, small window, opening from a real/copied Book, one local preference and a second Book remaining unchanged. A component fixture proves neither page ownership nor the surrounding product flow.

### A4 — Medium: native-state resumption is the right architecture, but its central promise is not yet demonstrated

**Proven design limit.** `planner.mjs:181` treats any active take as a reuse candidate and proposes `get_take`; it does not establish that the take is current, accepted or suitable. Semantic preconditions and many decisions are prose, while dependencies primarily join operations. This is consistent with an agent worklist and is not a scheduler bug. However, restarting an agent mid-work can repeat board/candidate generation unless it resolves existing native jobs, decisions and critiques correctly. A plan digest does not lock sources or mark progress.

**Requirement:** retain the modest product promise. Prove one interruption/resumption using native records: queued job, waiting board decision, selected predecessor, then a trim/pick change. The fresh agent must discover the next real action and avoid duplicate GPU jobs. If the proof fails, improve native projection/reuse diagnostics rather than creating a second progress store. Treat `ready`, `ok` and `arguments_complete` as separate facts, never a production-ready badge.

### A5 — High for scene correctness: accepted story, observed image and geometry hypothesis must remain distinct

**Current evidence:** the session README records four aerial-only failures and three top/side failures; none qualifies a production opening. I inspected the shipped whole original S plate, raw selected candidate2, and top+W+S result. The last image still places the actors on the ring area rather than clearly outside it. Candidate2 is visibly an elongated derived aerial; selecting it as an input does not measure source proportions or make all its geometry canonical. I did not inspect all native videos or listen to sound in this consultation.

**Implication:** a better strategy catalogue cannot repair this data/control problem. R271 is a preparation requirement, not a sufficiency theorem. Camera labels and `genuine_view:true` do not calibrate a camera. The top/side trial's camera plate also supplies composition, so no isolated top-view benefit has been established. Preserve the negative evidence and the user's raw candidate2 choice.

**Next owner:** a generated crack, dropped object or repeated action is initially an observation tied to a take/frame and source version. Existing story/location state remains accepted authority; use the normal canon/proposal policy when that observation should persist. Carry action phase across cuts separately from camera choice. Add this in the planned native world-state owner, not Director snapshots or reference metadata. A side-angle frame must not silently adopt a fresh undamaged floor just because it looks attractive. No more rerolls are recommended in this turn.
