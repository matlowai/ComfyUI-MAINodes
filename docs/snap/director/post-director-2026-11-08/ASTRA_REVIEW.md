## Disagreements and corrections to bind future work

1. **Do not interpret the addenda as blanket approval.** Intake §0 rightly preserves the running test. Its later assignment and Interface §11 must be implemented only as the user's next authorized work. Existing explicit approval continues to apply; no repeated permission ceremony for the same action. This review does not block the coordinator's already authorized verified WIP push.

2. **No new confirmation merely because an action arrived through speech or chat.** Intake §2 correctly separates user intent from actor attribution, but “ask for a UI gesture” must be conditioned on actual existing semantics. For this test, the real chat reply already authorized native acceptance by the agent and its receipt truthfully says agent. Preserve that pattern. A future voice transcript is not permission by itself, but an explicit, unambiguous instruction from an authorized user need not be asked again solely due to modality. Resolve the exact pending object/version and use the native route.

3. **Conversational style is not autonomy.** “Exploratory” means fewer unnecessary questions and more useful reversible progress within current scope. It cannot change Book canon rules, install settings, GPU authority, exports or page ownership. Conversely, “cautious” should not repeatedly reconfirm an already authorized task. The sample `new_project_creation: explicit-permission` must accept an existing instruction such as “make a separate experiment” as that permission.

4. **Autonomous learning needs a narrow exception to immediate activation, not removal of SNAP-R95.** Both `save_instruction` and `save_skill` are current, intentionally direct operations. The proposed optimizer protocol is new behavior that must be stated as such. Start with a documented candidate workflow outside active records; do not add a global “all agent changes need review” switch. Revisions requested by the person remain ordinary customization. Measure synthesized general lessons before promotion. `save_skill` supports versions over existing pack skills, not arbitrary new runtime skill names (`instructions.js:254–255`); the new intake skill starts as a canonical pack file.

5. **“Same native permission path” does not guarantee honest UI labels.** The Room discrepancy above means the shared tool architecture is necessary but insufficient. Reproduce managed-agent Room candidate selection and take judgment on disposable records; inspect actual stored actor labels. Also test an agent on a shared person's tab: current `pressedBy` classifies managed+driver, not every driver. A driver flag alone cannot distinguish a real human clicking while an agent holds the page. Prefer truthful executor/channel metadata over claiming human provenance from a DOM click. Keep authority and attribution as separate questions.

6. **Local-only is a product rule, not just a default provider preference.** Interface §5 allows an approved remote speech provider, but current pack AGENTS and SNAP-R18 prohibit Snap internet requests. For this checkout, implement local capture/approved local processing or use the user's existing conversational client. A browser recognition API is not automatically local: MDN documents server-based recognition in some browsers and a separate locality control. Do not ship a remote fallback under an “opt-in” label. Any future product rule change would be an explicit separate decision, never implicit in this addendum. [MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition).

7. **Do not build a new text dispatcher before proving a missing seam.** Interface packets 7–9 risk turning a useful optional front door into a second agent application. Current chat already interprets intent; Snap already dispatches tools. An eventual native text card should carry a target and native action/result, not reproduce reasoning, chat storage, permission policy or job state.

8. **Accessibility should lead voice, and numeric controls can satisfy two needs.** Room focus repair and same-data set-plan fields are immediate value. The numeric editor can provide keyboard and click/tap alternatives; a separate click-click canvas mode is optional if the numeric path fully covers the drag functionality. WAI explicitly separates keyboard access from single-pointer alternatives and permits a suitable text input alternative. Do not expand the first fix to every imagined interaction style. [WAI dragging guidance](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

9. **Do not overstate preflight.** Backend node schema, selected files, wiring and execution readiness are different evidence. Classify each check as pass/fail/unverified; a missing custom validation capability is not a fake green result. Do not execute arbitrary custom node validation hooks during a “read-only” check unless their side effects are understood. Avoid new quality-oriented input rejection, silent model substitutions or UI-recommendation caps. Preserve optional inputs, dynamic sockets and actual backend contracts.

10. **Use existing capability projections before introducing a registry.** Method readiness already exists. Improve its precise diagnostics only where needed, with the target server and source catalog revision. A preflight fingerprint should identify the target/observed schema without becoming persistent user/device tracking. Do not add broad session metadata to inference or model code.

11. **A compatibility harness is an extension, not a greenfield invention.** There is already a Nodes 2.0 switch smoke case. Begin with value truth and round-trip cases on the installed frontend; add 50/200/500-node performance measurements only after correctness and an actual need. Upstream issue anecdotes in Interface §2 are not failures reproduced here. No Vue rewrite is justified from the addendum.

12. **Neither a schema unit test nor a weighted score is an agent-quality evaluation.** Intake §11's 24 categories are a good initial coverage checklist. Freeze training/regression cases separately from untouched evaluation cases before optimizing. Record model/effort, prompts, visible state, actual calls, corrections, latency and judge disagreement. The ninja example and current dogfood are known cases, not held-out proof. Score wrong-project writes, fake human labels and unauthorized actions separately from soft usefulness; do not average them away. The weights in Interface §7 are planning judgments; their arithmetic does not establish empirical benefit. Use ordinal priorities until measured differences warrant a more precise comparison.

## Acceptance details that prevent misleading success

- **Intake:** evaluate requests with no task, explicit new experiment, named existing project, duplicate names, “thoughts only”, unavailable Snap, hostile screenshot text, unavailable original motion, H3/non-H3 Dial mismatch, mid-turn project correction and already-given permission. Compare useful next actions, not exact response wording. A fixtures-only parser suite cannot establish fewer interruptions in a real agent.
- **Authority:** record human direction separately from actor/channel. A simulated human response is labeled test evidence. Existing Story5/style2 is not a fresh approval question. A generic “yes” must resolve a specific current proposal and cannot be reused after another decision replaces it. Keep native revision and idempotency behavior.
- **Room:** moving focus is deliberate after an action, not on every incoming job. Do not rebuild a focused reason input when the mouse is elsewhere. Native modal behavior requires an inert background and contained focus; use a truthful nonmodal design if that is the intended product. WAI also calls for a sensible close-focus destination. [WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
- **Learning:** optimize fewer wrong assumptions and better recoveries, not merely fewer questions or higher acceptance. A user accepting a final image does not validate every setting. Save the exact skill version separately in the evaluation artifact: the current render instruction hash intentionally excludes on-demand skill text (`instructions.js:10–11,163`). Do not claim existing render pins reproduce a learned policy when they do not.
- **Audio:** selected provider locality must be evidenced. A loopback service can itself call outward, so inspect its configured behavior and test egress denial. Record cold/warm latency, hardware/resource placement and cancellation using realistic names and short ambiguous commands; no universal performance claim from one clean utterance. Keep microphone utterances, generated dialogue, Cast references and QA reports separate. Do not run an always-listening or full-duplex experiment in the first slice.
- **Accessible media:** a structured description is assistance, not an objective substitute for the creator's aesthetic judgment. Cite frame/time and uncertainty. A sampled visual review and ASR transcript do not establish whole-video playback/listening.
- **Release:** syntax/unit, native browser, real assistive technology, actual speech, GPU, perceptual review and production deployment get separate rows. Report not run explicitly. Keep the existing critic accuracy and instruction-pin failures under their own owners; no score adjustment or generalized green badge from intake work.

## Open decisions, without blocking useful work

These become concrete review questions at the relevant slice; none requires interrupting the current tiny test or stopping the skill pilot.

1. For the first accessibility target, is the supported product surface the Snap overlay and native workflows, with the host graph separately scoped? Recommend yes; do not promise host-wide conformance without host testing.
2. Which real local screen-reader/browser combination is available for S3? Pick one supported setup and state coverage; do not require every OS before a narrow fix can ship.
3. Does the user want speech in Snap itself, or is speech in the existing conversation client sufficient? Demonstrate the text/keyboard flow first. That answer determines whether S10 is useful.
4. Which local speech provider is already installed, approved and suitable for short control utterances? Inventory without downloads; do not select from the mere presence of a heavyweight QA model.
5. What is the first measurable intake failure beyond the ninja example? S0 and baseline runs should supply it. Do not preselect an elaborate policy resolver in anticipation.
6. Who reviews candidate skill promotion and which scope is allowed for canaries? Default to a reviewed local artifact and one disposable/session evaluation; retain existing user-directed customization.
